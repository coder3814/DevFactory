# Spec template

The skeleton of a card's spec folder, for `grill` to fill in or a person to copy. The folder
sits at the profile's specs path (default `specs/<card>/`), is versioned with the code, and
holds `spec.md` and the sibling files described after it. The card holds the request and its
criteria; the spec holds everything else a builder needs, and cites criteria by their stable
IDs, never by position. What makes a spec Ready is in
[`definition-of-ready.md`](definition-of-ready.md); the conditions named below are its.

Each prompt in italics says what the section holds; replace it. Delete any line or section
marked *(when there is any)* that has nothing to say, and drop the marker where it stays.
Every other section stays, because silence there is not a valid answer. The header and the
sections run general to specific, in this order.

---

## `spec.md`

```markdown
# Spec: <card title>

| | |
|---|---|
| **Card** | <card ID and link> |
| **Version** | <n> |
| **Status** | <drafting / Ready / approved> |
| **Card revision** | <hash of the card revision checked against> |
| **Repo commit** | <commit checked against> |
| **Stamped** | <date> |
| **Request type(s)** | <feature / bug fix / refactor / data correction / other, every one that applies> |

**Failing scenario at the base revision** *(bug fix only)*: *the input or state that
triggers the defect, what happens, and what should happen.*

**Surface that must not change** *(refactor only)*: *the observable surface held unchanged,
with any requested change to it listed and excluded.*
```

## The stamp

The stamp is three header rows of `spec.md`:

- **Card revision**: the SHA-256 of the card's text, as lowercase hexadecimal. The text is
  the title, a line feed, then the description body as the tracker returns it, with every
  line matching the spec line's form, `Spec: <path> @ <commit>` (see "The spec line" in
  [`card-standard.md`](card-standard.md)), removed, every line ending normalised to a
  single line feed (a carriage return and line feed pair, or a lone carriage return,
  becomes a line feed) and trailing line feeds removed. Where the profile writes a part to a field other than the description, that
  field's content follows, each preceded by a line feed, in the card standard's part order.
  Comments, attachments, the column and team fields are not part of the text, so recording a
  comment or moving the card leaves the stamp matching.
- **Repo commit**: kept by an amendment, which runs no check; the head of the branch the
  spec lives on, as the readiness checker read
  it.
- **Stamped**: the date.

Stamp only after the last write to the card, since every fold changes the text. The spec
line is the exception: `grill` writes it after stamping and committing the spec, and the
card revision leaves it out.

The plugin's script is the one implementation, run as
`python ${CLAUDE_PLUGIN_ROOT}/scripts/devfactory.py`: `stamp --card <n>` prints
the card revision, and `stamp-check --card <n> --spec <dir>` compares it with the stamp's
and checks that the stamped Repo commit is an ancestor of the current head (Ready
condition 9.2). For a tracker the script cannot read, or a part the profile writes to
another field, the caller writes the card's text in the form above to a file and passes it
to either command as `--text <file>` in place of `--card`. Every skill, agent and hook that
compares a card with its stamp runs these commands and computes nothing itself, so a
mismatch means the card's text changed, never that two readers hashed differently.

## Sibling files

### `wireframe.*` *(when the interface determination is non-trivial)*

A static, dependency-free file matched to the surface, such as an HTML page for a web
interface or a text sketch for a terminal one. It grounds structure, fields, states and
interaction; it fixes aesthetics only when the profile's wireframe fidelity says so. Several
screens may share one file or take one each, named under Interface surface.

### `gaps.md`

The gap record. Gaps start at Ready: a question answered before the spec first earns Ready
is folded into the card or the spec, not recorded as a gap. From Ready onward, every
question asked, every refused acceptance and every Done-check miss is an entry. Entries are
appended, newest last, by `gaps add <dir> --stage <stage> --question <text> --condition
<condition>`, adding `--resolved <version>` when the resolving amendment already exists;
the command writes this form with the date:

```markdown
## <date> — <stage>

- **Question or refusal:** <the question as asked, or the refusal in the requester's words>
- **Let through by:** <Ready or Done condition, for example Ready 3.2>
- **Resolved by:** <amendment version, or "open">
```

The stage is the card's lifecycle stage when the entry is made: Approval, Development, Done
or Acceptance. Done condition 4.2 requires every entry to name its resolving amendment, and
`gaps check <dir>` fails while any entry is still `open`.

Gap records survive release. At release, before the spec folder is deleted, its `gaps.md`
entries are appended to the project's ledger, `.devfactory/gaps.md`, each heading prefixed
with the card ID and the spec's request types (`## <card> (<types>) — <date> — <stage>`),
by `gaps ledger <dir> --card <n> --types <types> --ledger .devfactory/gaps.md`, so `curate`
can still group by request type after the spec is gone. The readiness checker reads the
ledger and every live spec's `gaps.md` before grilling, and `curate` reads the same set.

### `receipts.md`

The receipts. A check judges once, in the stage that produces what it judges; a later stage
compares a fingerprint instead of judging again. When a check passes, its skill writes a
receipt here: the fingerprint of everything the check read, field by field. A later stage
runs `receipt check` and goes on without the check when it prints `match`; any `differs`
line, or `no-receipt`, means the check runs as before, and a pass writes a new receipt.
Only `devfactory receipt write` writes this file and only `devfactory receipt check` reads
it; nobody edits it by hand.

- **Request**, written by whichever card skill or `grill` gate finds that the card meets the
  Definition of Request: `receipt write <dir> --check request --card <n>` (or `--text
  <file>`) `--facts <file>`. Its fields are the Card revision, as "The stamp" defines it;
  the Card facts, a hash of the facts file; the Standard, the plugin's version with a hash of
  its references and agents, so an edit to them changes it even without a version bump; and the
  Profile, a hash of the profile and its team modules. The facts file holds, one per line,
  everything else the card reviewer read about the card, as raw values from the tracker:
  `field <name>: <value>` for each team field, `comment <date> <author>: <text>` for each
  comment with its whole text on the one line, `attachment <name> <size> <date>` for each
  attachment, `parent <id>` for its parent and `sub-issue <id>` for each sub-issue in the
  tracker's order, and `related <what>: <value>` for each piece of related data a team
  module names. Order and spacing do not matter, except among the sub-issue lines, whose
  order is the one the work order is judged against. A card's first passing review creates this folder
  to hold the receipt, so the folder exists before `spec.md` does; a folder without
  `spec.md` is not a spec.
- **Ready**, written by `grill` when its last check finds the spec Ready, and by
  `check-ready` when its check finds nothing open: `receipt write <dir> --check ready --specs
  <file>`, the file naming, one per line, every spec folder the check measured together,
  written in the folder of the card the check was run for (the parent, for a parent issue).
  Its fields are the Specs measured; the Specs content, a hash of every file in them except
  `receipts.md`, with the Status row's value left out, so approval keeps it matching; the Gap
  sources, a hash of the ledger and every live `gaps.md`; the Standard; the Profile; and the
  Repo commit, the head the check read. The Repo commit matches while that commit is an
  ancestor of HEAD and nothing outside the specs path and `.devfactory/` differs between
  them, since everything under those is fingerprinted on its own.

### `evidence/`

What the Done judge consumes, added during development. One subfolder per criterion ID
(`evidence/C1/`, `evidence/C2/`, …), holding the artifacts that criterion's evidence row
promised. Beside each artifact sits a sidecar file of the same name with `.txt` appended,
holding one line:

```text
revision: <commit> | checkpoint: <environment> | produced by: <command or procedure>
```

The revision is the commit the artifact was captured at, and evidence is captured after the
last commit that changes the code it shows.

`evidence-check <dir> --criteria <file> --base <base revision>` checks the folder: a
non-empty subfolder for every criterion ID in the file, one per line as `criteria-ids`
prints them, and a sidecar in this form beside every artifact (Done conditions 2.1 and
3.2). Inside a repository it also checks that every file in those subfolders is committed
as it stands, so a clean checkout has it, that each sidecar's revision is a commit HEAD
descends from, or one whose change a rebase carried into HEAD's history unaltered (`git
cherry`), and that its checkpoint is one the criterion's evidence plan row names, compared
without regard to case. Given the base revision, it refuses an artifact as stale when a
code file the change set touches (changed between the base and HEAD) differs between the
sidecar's revision and HEAD. The test compares content, so a rebase that rewrote commit ids
or brought in other work leaves evidence current, and so do later commits that touch only
the specs path, `.devfactory/` or a path the profile's Specs entry lists as Not code, such as
where change notes go. An artifact whose revision is the base or an ancestor of it, such as
a failing run recorded at the base, is a capture of the base on purpose and is not tested.
