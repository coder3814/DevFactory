# Spec template

The skeleton of a card's spec folder, for `grill` to fill in or a person to copy. The folder
sits at the profile's specs path (default `specs/<card>/`), is versioned with the code, and
holds `spec.md` and the sibling files described after it. The card holds the request and its
criteria; the spec holds everything else a builder needs, and cites criteria by their stable
IDs, never by position. What makes a spec Ready is in
[`definition-of-ready.md`](definition-of-ready.md); the conditions named below are its.

Each prompt in italics says what the section holds; replace it. Delete any line or section
marked *(when there is any)* that has nothing to say, and drop the marker where it stays.
Every other section stays, because silence there is not a valid answer. The header and the
sections run general to specific, in this order.

---

## `spec.md`

```markdown
# Spec: <card title>

| | |
|---|---|
| **Card** | <card ID and link> |
| **Version** | <n> |
| **Status** | <drafting / Ready / approved> |
| **Card revision** | <hash of the card revision checked against> |
| **Repo commit** | <commit checked against> |
| **Stamped** | <date> |
| **Request type(s)** | <feature / bug fix / refactor / data correction / other, every one that applies> |

**Failing scenario at the base revision** *(bug fix only)*: *the input or state that
triggers the defect, what happens, and what should happen.*

**Surface that must not change** *(refactor only)*: *the observable surface held unchanged,
with any requested change to it listed and excluded.*

## Decisions delegated to the developer

*The calls grilling identified as the developer's under
[`decision-line.md`](decision-line.md), so the builder knows they are its to make.*

- *The call, and what bounds it.*

### Log

*Written during development, one line per call made: the call, the choice, the reason.*

- *<call> — <choice> — <reason>*

## Boundaries

### Excluded

- *What a reader might assume is included, and why it is not.*

### Deferred *(when there is any)*

- *What is kept alive outside this card, why, and where it is tracked.*

### Edge behaviour

| Criterion | Edge | Specified, excluded or delegated |
|---|---|---|
| C<n> | *a limit, an empty or extreme input, a failure path, a concurrent or repeated action* | *the behaviour, or "excluded, because …", or "delegated"* |

## Dispositions

*One line per fixed concern. "Not applicable, because …" is an answer; a blank is not.*

| Concern | Disposition | Demands (criterion or evidence row) |
|---|---|---|
| Existing data changed | | |
| Security | | |
| Performance | | |
| Release sequencing | *does the change need anything before or after the deploy* | |
| Owner steps | | |
| *<each extension the profile adds>* | | |

## Interface surface

**Determination:** *non-trivial / trivial, because … / not applicable, because …*

**Wireframe** *(non-trivial only)*: *its path beside this file, the pages or screens it
covers, and when it was approved.*

## Data population *(when the card's rules act on existing data)*

**Population:** *what was read, where, and at which point in time.*

| Rule | Rows |
|---|---|
| *the rule as the card states it* | *count* |

**Rows no rule covers:** *each, or each class of them, with how it is resolved: a rule, an
exclusion or a delegation.*

## Evidence plan

*One row per criterion. Each row could be failed by a delivered artifact.*

| Criterion | Shown by | What it will show | Under what condition | Generated by | Checkpoint |
|---|---|---|---|---|---|
| C<n> | *test, image, log, query or output* | | | *the command or procedure* | *a profile environment* |

| Step | Who | Moment in the run |
|---|---|---|
| *approve a mock-up, sign in somewhere, run something in a protected environment* | *the requester, or the role the profile names* | *before the build, after C<n> or a named sub-issue merges, after the deploy* |

|---|---|---|---|
```

## Sibling files

### `wireframe.*` *(when the interface determination is non-trivial)*

A static, dependency-free file matched to the surface, such as an HTML page for a web
interface or a text sketch for a terminal one. It grounds structure, fields, states and
interaction; it fixes aesthetics only when the profile's wireframe fidelity says so. Several
screens may share one file or take one each, named under Interface surface.

### `gaps.md`

The gap record: one entry per question asked after Ready, per refused acceptance, and per
Done-check miss. The readiness checker reads every spec's gap record before grilling, and
`curate` reads them across specs. Entries are appended, newest last:

```markdown
## <date> — <stage>

- **Question or refusal:** <the question as asked, or the refusal in the requester's words>
- **Let through by:** <Ready or Done condition, for example Ready 3.2>
- **Resolved by:** <amendment version, or "open">
```

The stage is one of the lifecycle stages: Development, Done or Acceptance. Done condition 4.2
requires every entry to name its resolving amendment.

### `evidence/`

What the Done judge consumes, added during development. One subfolder per criterion ID
(`evidence/C1/`, `evidence/C2/`, …), holding the artifacts that criterion's evidence row
promised. Beside each artifact sits a sidecar file of the same name with `.txt` appended,
holding one line:

```text
revision: <commit> | checkpoint: <environment> | produced by: <command or procedure>
```
